## 一、技術選型

| 層次 | 選擇 | 理由 |
|------|------|------|
| HTTP 框架 | Hono | 輕量、型別安全、支援 Node.js / Edge Runtime |
| ORM | Prisma（multiSchema） | 支援雙 schema 隔離，型別推導完整 |
| 驗證 | Zod | 與前端共用型別定義 |
| WebSocket | Node.js `ws` | AGENT_MODE 的 /ws/agent（bot 端網頁與後端的雙向通道） |
| 排程 | `node:timers`（`setInterval`） | 輕量，無需外部佇列 |
| 日誌 | `pino` | 結構化 JSON log，易於集中收集 |

> ⚠️ **單進程限制**：Bot Session 狀態儲存於 `activeSessions`（in-memory Map）。
> 此服務**必須以單一 Node.js 進程**執行，不可使用 `cluster`、`worker_threads`、PM2 cluster mode
> 或多副本水平擴展——各 worker 擁有獨立 Map，跨進程的 WS 事件無法路由到正確的 session，
> 喚醒詞偵測與摘要觸發將完全失效。若需高可用，請改以單進程 + 進程監控（PM2 fork mode）部署。

## 三、程式進入點（`src/index.ts`）

```typescript
import { Hono } from 'hono'
import { cors } from 'hono/cors'
import { authMiddleware } from './middleware/auth'
import { errorHandler } from './middleware/error-handler'
import { requestLogger } from './middleware/logger'
import { registerRoutes } from './routes'
import { startIndexingPoller } from './jobs/indexing-poller'
import { restoreActiveSessions } from './sessions/session-manager'

const app = new Hono()

// ── 全域 Middleware ──────────────────────────────
app.use('*', requestLogger())
app.use('*', cors({ origin: process.env.APP_CORS_ORIGINS!.split(',') }))
app.use('*', authMiddleware)   // 所有路由都需要認證（路由無 /api/ 前綴，不可用 /api/*）

// ── 路由 ─────────────────────────────────────────
registerRoutes(app)

// ── 錯誤處理 ─────────────────────────────────────
app.onError(errorHandler)

// ── Background Jobs ──────────────────────────────
startIndexingPoller()         // 每 30 秒輪詢 Dify 索引狀態

// ── Dify API Key 啟動驗證 ────────────────────────
// 驗證 DIFY_DATASET_API_KEY 是否有效（呼叫 GET /datasets，最多取 1 筆）。
// 此 key 同時用於 meetbot 後端（KB 操作）和 Dify 平台 Chatflow 的 HTTP Request node。
// 若 key 無效（401），Chatflow 的 RAG 查詢靜默失效（回傳固定字串），
// 而 meetbot 後端收到 HTTP 200 無法感知；啟動時驗證提供早期警示。
//
// ⚠️ 此驗證僅確認 meetbot 後端的 DIFY_DATASET_API_KEY 有效。
// Chatflow 內部的 HTTP Request node 需要在「Dify 平台 Settings → Environment Variables」
// 另行設定相同的 key（變數名 DIFY_DATASET_API_KEY）。兩邊需獨立設定。
await (async () => {
  try {
    const res = await fetch(
      `${process.env.DIFY_API_BASE}/datasets?limit=1`,
      { headers: { Authorization: `Bearer ${process.env.DIFY_DATASET_API_KEY}` } }
    )
    if (!res.ok) {
      logger.error(
        { status: res.status },
        'STARTUP: DIFY_DATASET_API_KEY validation failed — Knowledge Base operations will fail. ' +
        'Also confirm the same key is set in Dify platform env vars for the Chatflow HTTP Request node.',
      )
    } else {
      logger.info('STARTUP: DIFY_DATASET_API_KEY validated successfully')
    }
  } catch (err) {
    logger.warn({ err }, 'STARTUP: Dify API reachability check failed (network error) — proceeding anyway')
  }
})()

// ── 啟動時恢復進行中的 Session（服務重啟後） ──────
await restoreActiveSessions() // 查詢 DB 中 status=ACTIVE 的會議，重建 WebSocket

export default { port: Number(process.env.APP_PORT ?? 4000), fetch: app.fetch }
```

## 四、認證 Middleware（`src/middleware/auth.ts`）

```typescript
import type { MiddlewareHandler } from 'hono'
import { prisma } from '../lib/prisma.js'
import type { AppEnv } from '../types/hono.js'

export const authMiddleware: MiddlewareHandler<AppEnv> = async (c, next) => {
  const token = c.req.header('Authorization')?.replace('Bearer ', '')
  if (!token) {
    return c.json({ error_code: 'UNAUTHORIZED', message: '缺少 Authorization header' }, 401)
  }

  const userToken = await prisma.userToken.findUnique({
    where: { token },
    include: { user: true },
  })

  if (!userToken || (userToken.expiresAt && userToken.expiresAt < new Date())) {
    return c.json({ error_code: 'UNAUTHORIZED', message: '無效的 token' }, 401)
  }

  c.set('userId', userToken.user.id)
  c.set('userEmail', userToken.user.email)
  c.set('userName', userToken.user.name)
  c.set('maxConcurrentBots', userToken.user.maxConcurrentBots)

  await next()
}
```

> **2026-08 變更**：身份層從 Vexa 的 `public.api_tokens` / `public.users`（`$queryRaw`）
> 搬到 app 自管的 `app.user_tokens` / `app.users`（Prisma model）。連帶消失的東西：
> - **token scope**（`bot` / `browser` / `tx`）與 `requireBotScopes()`：那是 Vexa api-gateway
>   分路徑驗證的產物，Recall 用服務自己的 API key，沒有 per-user scope 這回事。
>   錯誤碼 `INSUFFICIENT_SCOPE` 一併移除。
> - **`vexaToken` / `vexaApiTokenId` context 變數**：不再需要「拿使用者的 token 去打 provider」。

### token 從哪裡來（`src/routes/internal.ts`）

前端 NextAuth 登入時打 `POST /internal/token`（header `x-internal-secret`），
後端 `prisma.user.upsert` + 重用未過期 token，沒有才新發一顆 32 bytes hex。

⚠️ `INTERNAL_AUTH_SECRET` 未設定＝端點回 503。前端拿不到 token 時**登入仍然成功**，
只是 `session.authToken` 是 null，之後每個 API 都 401——所以前端在三條失敗路徑上都印明確錯誤，
`start.ps1` 也會自動產生並同步前後端的密鑰。

### 5.1.1 Provider 邊界型別（`src/provider/types.ts`）

各家 provider 的原始 payload **一律在 adapter 內正規化**，session 層之後只看統一 schema：

```typescript
/** 統一逐字稿段落（normalize.ts 負責把 provider 原始格式轉成這個） */
export interface TranscriptSegment {
  segmentId: string | null
  text:      string
  speaker:   string | null
  startTime: number   // 秒
  endTime:   number   // 秒
  language:  string | null
}

/** 會議聊天室訊息（用於聊天室喚醒詞） */
export interface ChatMessageEvent {
  sender:     string

  timestamp:  number   // Unix ms
  isFromBot:  boolean

```

> **為什麼正規化要在 adapter 內、而且是純函式**：換 provider 時只有 `normalize.ts` 要動，
> 喚醒詞、插話、摘要全鏈路一行不改。這也是全專案唯一有針對性單元測試的轉換層
> （`tests/unit/backend/provider/normalization.test.ts`）。
>
> Vexa 時代這裡還有 `VexaRestSegment`（欄位是 Pydantic alias 的 `start`/`end`，不是
> `start_time`/`end_time`）與 snake_case 的 `VexaChatMessage`，已隨 Vexa 一併移除。

### 5.2 Session Manager（`session-manager.ts`）

> 2026-08 全面改寫：原本是「以邀請者 token 建 per-session Vexa WebSocket、訂閱三條 Redis
> channel」。移除 Vexa 之後，逐字稿與聊天室訊息改由 **Recall webhook** 推進來，
> session 層只認 provider 抽象層給的 `LiveHandlers`，不再自己管 WS。

四個對外函式：

| 函式 | 做什麼 |
|------|--------|
| `startBotSession()` | 派 bot、等 admission、成功轉 ACTIVE、失敗轉 FAILED |
| `closeSession()` | 主動請 bot 離開並清掉 Map entry（bot/leave、reinvite 前的防禦性清理） |
| `handleSessionClose()` | 會議結束的單一收斂點：更新終態 + 觸發摘要 |
| `restoreActiveSessions()` | 啟動時清理上次進程留下的殘局 |

#### `startBotSession()`

```
① 先把 MeetingSession 放進 activeSessions Map
   ⚠️ 順序關鍵：live handler 可能在 admitted 之前就收到事件，Map 裡沒有就會被丟掉
② botProvider.join(googleMeetUrl, options, handlers)
   ↳ 內部等待 bot 真的被准入（RECALL_ADMISSION_TIMEOUT_MS，預設 90 秒）
   ↳ 進不去（等候室沒人按、逾時、dispatch 失敗）→ throw
③ admitted → 回填 botSession，DB 轉 ACTIVE、寫 startedAt 與 nativeMeetingId
④ 發歡迎訊息、載入知識庫內容卡（供意圖分類判斷問題是否落在 KB 範圍）
⑤ 任一步失敗 → DB 轉 FAILED，並把 Map entry 清掉
```

> **為什麼 DB 不在 dispatch 成功當下就轉 ACTIVE**：ACTIVE 的語意是「蜜塔真的在會議裡」，
> 並發上限與前端狀態都靠它。bot 還在等候室就設 ACTIVE，會讓使用者以為成功、也白佔並發額度。

#### `buildLiveHandlers()`

provider 把即時事件交回來的四個入口，全部只做「查 session → 轉交」：

| handler | 交給誰 |
|---------|--------|
| `onSegment`（定稿逐字稿） | `handleTranscriptSegment`（喚醒詞/追問判斷）+ `recordConversation`（插話引擎） |
| `onPartial`（講到一半） | `handlePartialSegment`（喚醒詞快速確認，體感 ~1 秒）、`handleBargeIn` |
| `onChat`（聊天室訊息） | `handleChatMessage` + 記進 `chatLog`（會後併入逐字稿） |
| `onStatus`（bot 結束） | `handleSessionClose` |

#### `handleSessionClose()` — 摘要只跑一次的原子鎖

```typescript
// 第一行就從 Map 刪除，再做後續處理。
// 這不是風格問題：bot/leave 的 HTTP 請求與 provider 推來的「bot 已結束」事件會同時到，
// 兩條路都會呼叫本函式。先 delete 再處理，讓第二個呼叫查不到 session 直接返回，
// 摘要就只會生成一次。
const session = activeSessions.get(meetingInstanceId)
if (!session) return
activeSessions.delete(meetingInstanceId)
```

終態判定：provider 回報 `failed`（bot 在被准入前就結束）→ `FAILED`，不觸發摘要；
其餘 → `ENDED` 並在背景跑 `generateSummaryAsync`。

> **summary 哨兵**：`summary = null` 代表「還在生成中」（前端繼續輪詢）、
> `summary = ''` 代表「已嘗試但沒有內容」（前端停止輪詢）、有字串就是正常。
> 沒有 session 就沒有逐字稿可取，直接落 `''`——但更新條件帶 `summary: null`，
> 避免把已經寫好的真摘要蓋掉。

#### `restoreActiveSessions()` — 啟動時的殘局清理

```
階段一：PENDING 超過 5 分鐘 → FAILED（上次進程死掉留下的 zombie）
階段二：ACTIVE 一律 → ENDED（bot session 活在記憶體，重啟後接不回來）
        帶 summary: null 條件，不覆蓋已有摘要
階段三：ENDED + summary=null 且結束超過 10 分鐘 → summary=''（讓前端停止輪詢）
```

> Vexa 時代這裡會嘗試「用 creatorApiTokenId 查回 token → 重建 WS → 重接會議」，
> 甚至補跑摘要。Recall 沒有這條路：bot session 是活的連線與記憶體緩衝，
> 逐字稿也沒落 DB，重試只會拿到空陣列。與其假裝努力過，不如直接收尾。
> 根治要讓 segment 落 DB，見 `docs/13-系統現況與路線圖.md § 已知限制`。

### 5.3 喚醒詞偵測（`wake-word-detector.ts`）

語音輸入與聊天室輸入由 provider 抽象層的不同 handler 送進來（`onSegment` / `onPartial` / `onChat`），分開處理：

```typescript
// 中文：蜜塔/密塔/祕塔/秘塔/迷塔、小幫手
// 英文：Meeta/meeta/Mita/mita（語音辨識可能輸出英文拼寫）
const WAKE_WORD_REGEX = /[蜜密祕秘迷][塔搭]|小幫手|[Mm]eeta|[Mm]ita/
const DEBOUNCE_MS = 2000          // 2 秒內不重複觸發（跨語音和聊天室共用）
const MAX_PROCESSED_SEGMENT_IDS = 5000  // 防記憶體無界成長（長會議約 8 小時安全邊際）

// ── 語音輸入（provider 的 onSegment handler）────────────────────
// segment 已由 adapter 正規化成統一的 TranscriptSegment（見 5.1.1）。
export async function handleTranscriptSegment(
  session: MeetingSession,
  segment: { segment_id: string; text: string; speaker: string; start_time: number; end_time: number }
): Promise<void> {
  // 防重複：同一 segment_id 已處理過（provider 可能重送同一段的修訂版）
  if (!segment.segment_id || session.processedSegmentIds.has(segment.segment_id)) return

  // 防記憶體無界成長：超過上限時保留最新的一半（接受極小概率的重複觸發風險）
  if (session.processedSegmentIds.size >= MAX_PROCESSED_SEGMENT_IDS) {
    const ids = [...session.processedSegmentIds]
    session.processedSegmentIds = new Set(ids.slice(Math.floor(ids.length / 2)))
  }
  session.processedSegmentIds.add(segment.segment_id)

  const match = WAKE_WORD_REGEX.exec(segment.text)
  if (!match) return

  // 防重複觸發：2 秒內只觸發一次
  const now = Date.now()
  if (now - session.lastWakeAt < DEBOUNCE_MS) return
  session.lastWakeAt = now

  const question = segment.text
    .slice(match.index + match[0].length)
    .replace(/^[\s，。！？、…]+/, '')  // 去除語音轉文字常見的前置標點（例：「蜜塔，請問」截取後剩「，請問」）
    .trim()
  if (!question) return

  // 語音輸入 → 語音回覆
  await dispatchQuestion(session, question, 'voice')
}

// ── 聊天室輸入（provider 的 onChat handler）─────────────────────

export async function handleChatMessage(
  session: MeetingSession,
  chatMsg: ChatMessageEvent   // 欄位：sender, text, timestamp, isFromBot
): Promise<void> {
  // 忽略 Bot 自己發出的訊息，避免無限迴圈
  if (chatMsg.isFromBot) return

  const match = WAKE_WORD_REGEX.exec(chatMsg.text)
  if (!match) return

  // 防重複觸發：與語音共用同一個 lastWakeAt 計時器
  const now = Date.now()
  if (now - session.lastWakeAt < DEBOUNCE_MS) return
  session.lastWakeAt = now

  const question = chatMsg.text
    .slice(match.index + match[0].length)
    .replace(/^[\s，。！？、…]+/, '')  // 去除聊天室輸入常見的前置標點
    .trim()
  if (!question) return

  // 聊天室輸入 → 聊天室回覆
  await dispatchQuestion(session, question, 'chat')
}

// ── 問題分派（根據來源決定回覆管道）───────────────────────────────

// 超過此時間未提問，重置 Dify 對話（避免 conversation 過期 + 避免過長對話拖慢 LLM）
const CONVERSATION_IDLE_RESET_MS = 5 * 60 * 1000  // 5 分鐘

/**
 * 統一問答入口：選擇查詢路徑並管理 Dify 多輪對話 ID。
 *   有知識庫（difyDatasetId 非 null）→ Dify Chatflow RAG，帶 conversation_id 實現多輪連貫
 *   無知識庫（獨立會議）→ 最近 30 段逐字稿 + Claude 直接回答（無多輪上下文）
 *
 * `mode` 對應 dispatchQuestion 的 source：
 *   source="voice" → mode="voice"（後端截斷至 100 字；Chatflow 本身不含此分流邏輯）
 *   source="chat"  → mode="text"（不截斷）
 *
 * Dify conversation_id 管理策略：
 *   - 閒置超過 5 分鐘 → 重置 ID，下次問題開新對話
 *   - Dify 回傳錯誤（舊 ID 過期等）→ 自動重置後重試一次（建立新對話）
 */
async function resolveAnswer(
  session: MeetingSession,
  question: string,
  mode: 'voice' | 'text',
): Promise<string> {
  if (!session.difyDatasetId) {
    const { answer } = await answerFromTranscript(session, question)
    return answer
  }

  // 閒置重置：lastQuestionAt = 0 時（初始值）不重置（避免首次問答開新對話後立刻再重置）
  if (session.lastQuestionAt > 0 && Date.now() - session.lastQuestionAt > CONVERSATION_IDLE_RESET_MS) {
    logger.info({ meetingInstanceId: session.meetingInstanceId }, 'Dify conversation reset: idle timeout')
    session.difyConversationId = null
  }

  const callDify = async (conversationId: string | null) =>
    dify.askQuestion({
      datasetId: session.difyDatasetId!,
      question,
      mode,            // "voice" | "text"：後端截斷依據；Chatflow 本身無此分流邏輯
      userId: session.meetingInstanceId,
      conversationId,
    })

  try {
    const { answer, conversationId } = await callDify(session.difyConversationId)
    session.difyConversationId = conversationId || session.difyConversationId
    session.lastQuestionAt = Date.now()
    return answer
  } catch (err) {
    // Dify 錯誤（最常見：舊 conversation_id 已過期）→ 重置後重試一次
    if (session.difyConversationId) {
      logger.warn({ meetingInstanceId: session.meetingInstanceId }, 'Dify error, resetting conversation and retrying')
      session.difyConversationId = null
      const { answer, conversationId } = await callDify(null)
      session.difyConversationId = conversationId
      session.lastQuestionAt = Date.now()
      return answer
    }
    throw err
  }
}

async function dispatchQuestion(
  session: MeetingSession,
  question: string,
  source: 'voice' | 'chat'
): Promise<void> {
  const pendingVoice = session.difyDatasetId
    ? '好的，我收到了，正在查詢資料，請稍候。'
    : '好的，我收到了，正在查閱會議記錄，請稍候。'
  const pendingChat = session.difyDatasetId
    ? '收到你的問題，正在查詢資料中……'
    : '收到你的問題，正在查閱會議記錄……'

  // 語音模式：在查詢開始前就鎖住 isSpeaking，防止查詢期間第二次喚醒詞插入
  if (source === 'voice') {
    if (session.isSpeaking) return
    const PROMPT_TEXT = pendingVoice
    const promptEstimatedMs = Math.max(3000, (PROMPT_TEXT.length / 4) * 1000 + 1500)
    session.isSpeaking = true
    const lockTimer = setTimeout(() => { session.isSpeaking = false }, promptEstimatedMs + 10_000)

    try {
      await botProvider.speak(session.botSession!, {
        text: PROMPT_TEXT,
        provider: 'openai',
        voice: 'alloy',
      })

      const rawAnswer = await resolveAnswer(session, question, 'voice')

      // Chatflow Start 節點無 mode 變數，不含分流邏輯：後端兜底截斷確保語音回答不超過 100 字
      let answer = rawAnswer
      if (rawAnswer.length > 100) {
        const truncated = rawAnswer.slice(0, 100)
        const lastPunct = truncated.search(/[。！？…][^。！？…]*$/)
        answer = (lastPunct > 0 ? truncated.slice(0, lastPunct + 1) : truncated) + '……如果想了解更多，可以繼續問我。'
      }

      clearTimeout(lockTimer)
      const answerEstimatedMs = Math.max(3000, (answer.length / 4) * 1000 + 1500)
      setTimeout(() => { session.isSpeaking = false }, promptEstimatedMs + answerEstimatedMs)

      await botProvider.speak(session.botSession!, {
        text: answer,
        provider: 'openai',
        voice: 'alloy',
      })
    } catch (err) {
      clearTimeout(lockTimer)
      session.isSpeaking = false
      logger.error({ err, meetingInstanceId: session.meetingInstanceId }, 'dispatchQuestion voice failed')
    }
  } else {
    await botProvider.sendChat(session.botSession!, {
      text: pendingChat,
    })

    try {
      const answer = await resolveAnswer(session, question, 'text')
      await botProvider.sendChat(session.botSession!, {
        text: answer,
      })
    } catch (err) {
      logger.error({ err, meetingInstanceId: session.meetingInstanceId }, 'dispatchQuestion chat failed')
      await botProvider.sendChat(session.botSession!, {
        text: '抱歉，查詢時發生錯誤，請稍後再試。',
      })
    }
  }
}

// ── 逐字稿 Q&A（無知識庫路徑）──────────────────────────────────────
//
// 以最近 30 段逐字稿為 context，直接送 claude-sonnet-4-6 回答。
// 適用於獨立會議（difyDatasetId === null）。
// 不呼叫 Dify，直接使用 ANTHROPIC_API_KEY 呼叫 Claude API（無多輪上下文）。

async function answerFromTranscript(
  session: MeetingSession,
  question: string,
): Promise<{ answer: string }> {
  const allSegments = await botProvider.getTranscript(session.botSession!)
  const recentSegments = allSegments.slice(-30)   // 最近約 5~10 分鐘
  if (!recentSegments.length) {
    return { answer: '目前還沒有足夠的逐字稿內容可以回答，請稍後再試。' }
  }
  const context = recentSegments
    .map(seg => `[${seg.speaker || '參與者'}]: ${seg.text}`)
    .join('\n')

  const message = await anthropic.messages.create({
    model: 'claude-sonnet-4-6',
    max_tokens: 512,
    system: '你是在線的 AI 會議助理蜜塔（Meeta）。請根據提供的會議逐字稿片段，簡潔回答問題。若逐字稿沒有相關資訊，請說明無法從當前會議內容找到答案。',
    messages: [{
      role: 'user',
      content: `以下是近期的會議逐字稿片段：\n\n${context}\n\n請回答：${question}`,
    }],
  })
  const answer = message.content[0].type === 'text' ? message.content[0].text : '抱歉，無法取得回答。'
  return { answer }
}
```

邀請改為「**先建 pending 邀請、再由對方接受**」，可邀請尚未註冊者。完整生命週期與錯誤碼見

- **token 安全**：`generateToken()` 產生 `randomBytes(32).base64url` 明碼 + 其 `SHA-256` hash。

- **canView 基準權限**：建立邀請時強制 `canView: true`（與 `member.service.updateMemberPermissions` 的矯正一致）。
- **活動紀錄**：建立邀請寫 `MEMBER_INVITE`、接受寫 `MEMBER_ADD`（`activity.service.recordActivity`）。
- **擁有者檢視待處理邀請**：**不另設 list 端點**——`member.service.getMembers` 內聯查 `status=PENDING`

## 六、Dify 外部服務封裝（`src/lib/dify.ts`）

> **架構決策（v1.4，依 01-RAG_API_串接文件_v1.1 更新）**：Q&A、會議摘要、檔案摘要各自對應獨立的 Dify App，使用不同 API Key。
>
> ### Q&A：使用 Dify Chatflow（`01-edu2.yml`，`DIFY_WORKFLOW_API_KEY`）
>
> Dify 組員提供的 Chatflow（`docs/01-edu2.yml`）支援在 **runtime 動態傳入 `dataset_id`**，
> 工作流的 HTTP Request node 使用 URL 插值
> `https://api.dify.ai/v1/datasets/{{#1777452815445.dataset_id#}}/retrieve`，
> 完全動態，不需在 Dify 平台 hardcode dataset。
>
> Chatflow 內部流程（優於手動 Retrieve+Claude 的原因）：
> 1. **Gemini 2.5 Flash** 做雙語關鍵字提取（中→中+英，提升混語料召回率）
> 2. **hybrid_search**（語義 + BM25）+ Jina reranker-m0 重排，top_k=8，score ≥ 0.5 過濾
> 3. **Claude Opus 4**（`claude-opus-4-20250514`）依 context 嚴格回答
>
> `askQuestion` 需同時傳入 `dataset_id` 與 `mode`（`"voice"` 或 `"text"`）。
> `mode` 為後端截斷依據；Chatflow Start 節點無此變數，傳入後被忽略。
> 語音 100 字截斷邏輯由後端 `dispatchQuestion` 實作（見五之二節）。
>
> ### 會議摘要：獨立 Dify Workflow（`DIFY_MEETING_SUMMARY_WORKFLOW_API_KEY`）
>
> 會議摘要使用**獨立的 Dify App**，與 Q&A Chatflow **完全分離**：
> - 呼叫端點：`POST /workflows/run`（非 `/chat-messages`）
> - 先呼叫 `POST /files/upload`（使用相同 key）上傳逐字稿 `.md` 檔，取得 `file_id`
> - 傳入 `inputs.transcript`（file 物件，`transfer_method: "local_file"`）
> - 輸出：`data.outputs.result_json`（字串，需再 `json.loads`）
>   結構：`meeting_title` / `summary` / `key_topics` / `decisions` / `action_items: [{task, owner}]`
>
> ⚠️ `action_items` 每筆含 `task`（事項描述）與 `owner`（負責人，可空字串），
> 非舊版的純字串陣列，DB 欄位與 API 回應需對應調整。
>
> ### 檔案摘要：獨立 Dify Workflow（`DIFY_SUMMARY_WORKFLOW_API_KEY`）
>
> 使用者上傳檔案後，可選擇觸發檔案摘要 Workflow，快速了解檔案內容（獨立功能，不影響 RAG）：
> - 先上傳檔案至 `POST /files/upload`（使用 `SUMMARY_WORKFLOW_API_KEY`），取得 `file_id`
> - 觸發 `POST /workflows/run`，`inputs.file_arr` 與 `inputs.userinput.files` 帶入 file 物件
> - 多檔請**串行上傳**並間隔約 1 秒，避免 502
> - 輸出：`data.outputs.result_json`（字串，需 `json.loads`）
>   結構：`project_title` / `project_summary` / `covered_topics` / `file_count` / `outliers`（可為 `[]`）
>   ＋ `file_summaries: [{filename, title, category, summary, key_topics}]`
>
> ### ⚠️ 部署必做：`docs/01-edu2.yml` 匯入 Dify 後需手動設定 API Key
>
> 該檔案的 HTTP Request node 原含硬編碼 `Authorization: Bearer <dataset-...>`，
> 已替換為佔位符 `{{DIFY_DATASET_API_KEY}}`，不納入版本控制。
>
> **⚠️ 靜默失效風險**：若未在 Dify 平台設定此環境變數，Chatflow 的知識庫查詢
> （`/datasets/{id}/retrieve`）會回傳 401 並走 IF/ELSE false 分支，直接輸出「抱歉 沒有檢索到相關資訊」。
> meetbot 後端看到 HTTP 200，**無法感知 RAG 已完全失效**。
>
> 匯入 Dify 平台後，**擇一**執行：
> - 在 HTTP Request node 的 headers 欄位直接填入實際的 `dataset-...` API Key，或
> - 在 Dify 平台 **Settings → Environment Variables** 新增 `DIFY_DATASET_API_KEY = dataset-...`
>
> meetbot 後端呼叫 Chatflow 時使用 `DIFY_WORKFLOW_API_KEY`（`app-...` 格式），
> 與 Knowledge Base 操作的 `DIFY_DATASET_API_KEY`（`dataset-...` 格式）獨立。

```typescript
  // ⚠️ 若 Dify 平台修改此字串，需同步更新下方常數。
  const DIFY_NO_RESULT_SENTINEL = '抱歉 沒有檢索到相關資訊'
  if (answer === DIFY_NO_RESULT_SENTINEL) {
    logger.warn(
      { datasetId: params.datasetId },
      'Dify Chatflow returned no-result sentinel — possible cause: ' +
      'DIFY_DATASET_API_KEY not configured in Dify platform env vars ' +
      '(Settings → Environment Variables). Check 06-後端架構.md §六 部署必做。',
    )
  }

  return { answer, conversationId: data.conversation_id ?? '' }
}

// ── 逐字稿 MD 檔案上傳至 Dify Files API ─────────────────────

/**
 * 將逐字稿 Markdown 內容上傳至 Dify Files API，回傳 upload_file_id。
 * 此 ID 作為後續呼叫摘要工作流時的 transcript_file 參數。
 *
 * ⚠️ Dify Files API 以 multipart/form-data 上傳，回傳 { id, name, size, ... }
 * 使用 DIFY_MEETING_SUMMARY_WORKFLOW_API_KEY（與 Q&A Chatflow 完全獨立）。
 */
export async function uploadTranscriptFile(
  meetingInstanceId: string,
  markdownContent: string,
): Promise<string> {
  const form = new FormData()
  const blob = new Blob([markdownContent], { type: 'text/markdown' })
  form.append('file', blob, `transcript-${meetingInstanceId}.md`)
  form.append('user', meetingInstanceId)

  const res = await fetch(`${DIFY_BASE}/files/upload`, {
    method: 'POST',
    headers: { Authorization: `Bearer ${MEETING_SUMMARY_KEY}` },
    // ⚠️ 不設 Content-Type：讓 fetch 自動加上正確的 multipart boundary
    body: form,
    signal: AbortSignal.timeout(30_000),
  })
  if (!res.ok) {
    throw new Error(`Dify file upload error: ${res.status} ${await res.text()}`)
  }
  const data = await res.json()
  return data.id as string   // upload_file_id，用於 transcript_file 欄位
}

// ── 會議摘要（Dify Workflow，mode="summary"，以 file 傳入逐字稿）────────

/**
 * 生成會議摘要，透過獨立的 Dify 會議摘要 Workflow（DIFY_MEETING_SUMMARY_WORKFLOW_API_KEY）。
 * 依 01-RAG_API_串接文件_v1.1：
 *   - 端點：POST /workflows/run（非 /chat-messages）
 *   - 逐字稿以 file 物件傳入 `inputs.transcript`，先由 uploadTranscriptFile 上傳
 *   - 輸出：data.outputs.result_json（字串，需 json.loads）
 *     結構：meeting_title / summary / key_topics / decisions / action_items: [{task, owner}]
 *
 * ⚠️ action_items 每筆含 `task`（描述）與 `owner`（負責人，可空字串），
 * 非舊版的純字串陣列，DB actionItems 欄位格式已同步更新（見 03-資料庫Schema設計.md）。
 */
export async function generateSummary(params: {
  difyFileId: string          // 由 uploadTranscriptFile 上傳後取得的 upload_file_id
  meetingInstanceId: string   // 作為 Dify user 識別符（用於 Dify 用量追蹤）
}): Promise<{ summary: string; actionItems: Array<{ task: string; owner: string }>; keyTopics: string[]; decisions: string[] }> {
  const res = await fetch(`${DIFY_BASE}/workflows/run`, {
    method: 'POST',
    headers: {
      Authorization: `Bearer ${MEETING_SUMMARY_KEY}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({
      inputs: {
        transcript: {
          type: 'document',
          transfer_method: 'local_file',
          upload_file_id: params.difyFileId,
        },
      },
      response_mode: 'blocking',
      user: params.meetingInstanceId,
    }),
    signal: AbortSignal.timeout(60_000),   // 摘要較長，給 60 秒
  })
  if (!res.ok) {
    throw new Error(`Dify meeting summary error: ${res.status} ${await res.text()}`)
  }
  const data = await res.json()
  if (data.data?.status !== 'succeeded') {
    throw new Error(`Dify meeting summary workflow failed: ${JSON.stringify(data.data)}`)
  }
  try {
    // result_json 為字串，需 json.loads；可能有 ```json ``` markdown 包裹
    let raw: string = data.data.outputs?.result_json ?? ''
    raw = raw.replace(/^```json\s*/i, '').replace(/\s*```$/, '').trim()
    const parsed = JSON.parse(raw)
    return {
      summary:     parsed.summary     ?? '',
      actionItems: parsed.action_items ?? [],  // [{task, owner}]
      keyTopics:   parsed.key_topics   ?? [],  // string[]
      decisions:   parsed.decisions    ?? [],  // string[]
    }
  } catch {
    // fallback：整段文字作為 summary，其他欄位為空
    return { summary: data.data.outputs?.result_json ?? '', actionItems: [], keyTopics: [], decisions: [] }
  }
}
```

```typescript
import { prisma } from '../lib/prisma'
import { getIndexingStatus } from '../lib/dify'

export function startIndexingPoller(): void {
  setInterval(async () => {
    try {
      // 查詢所有 PENDING / PROCESSING 的材料（含所屬專案的 difyDatasetId）
      const materials = await prisma.material.findMany({
        where: {
          indexingStatus: { in: ['PENDING', 'PROCESSING'] },
          deletedAt: null,
          difyBatch: { not: null },
        },
        include: { project: { select: { difyDatasetId: true } } },
      })

      await Promise.allSettled(materials.map(async (material) => {
        const status = await getIndexingStatus(
          material.project.difyDatasetId,
          material.difyBatch!
        )
        await prisma.material.update({
          where: { id: material.id },
          data: { indexingStatus: status.status, indexingError: status.error ?? null },
        })
      }))
    } catch (err) {
      logger.error({ err }, 'indexing-poller failed')
    }
  }, 30_000)
}
```

## 八、服務重啟恢復策略

`activeSessions` 是純記憶體的 Map，進程一死就沒了。啟動時 `restoreActiveSessions()`
（`src/sessions/session-manager.ts`）負責把 DB 裡的殘局收乾淨。

```
階段一：status = PENDING 且建立超過 5 分鐘 → FAILED
        （上次進程在「派 bot」中途死掉留下的 zombie）

階段二：status = ACTIVE → ENDED + endedAt + summary=''
        帶 summary: null 條件，不覆蓋已寫好的摘要

階段三：status = ENDED 且 summary IS NULL 且結束超過 10 分鐘 → summary=''
        （摘要在背景生成到一半被重啟打斷，前端會一直輪詢，落哨兵讓它停）
```

> **為什麼不「重接會議」**：Vexa 時代 DB 存了 `vexaMeetingId` + `creatorApiTokenId`，
> 重啟後可以查回 token、重建 WS、甚至用 REST 補抓逐字稿生摘要。Recall 沒有這條路——
> bot session 是活的 webhook 連線與記憶體緩衝，逐字稿也沒落 DB，重試只會拿到空陣列。
> 所以現在一律收尾，不假裝能救。
>
> **代價寫在這裡以免被當成 bug**：後端重啟時進行中的會議，蜜塔會停止回應
> （Recall 的 bot 可能還留在會議裡，需人工把它請出去或等它自己逾時），
> 該場會議也不會有摘要。根治要讓 segment 落 DB，見 `13-系統現況與路線圖.md § 已知限制`。

⚠️ **單進程限制**：因為狀態全在記憶體，**不可多進程部署**。
PM2 必須用 fork mode（不可 cluster），否則兩個進程各自持有一半的 session，
webhook 打到沒有該 session 的進程就會被丟掉。

## 九、錯誤處理策略

### 9.1 三方操作的 Rollback 原則

| 操作 | 失敗點 | Rollback 行為 |
|------|--------|---------------|
| 上傳檔案 | Storage 上傳後 Dify 失敗 | 刪除 Storage 檔案 |
| 上傳檔案 | Dify 上傳後 DB 寫入失敗 | 刪除 Storage + Dify 文件 |
| 建立專案 | Dify 建立後 DB 寫入失敗 | 刪除 Dify dataset |
| 刪除檔案 | 任一步驟失敗 | 記錄 error log，標記異常，不對使用者拋錯（後台補清理） |

### 9.2 統一錯誤回應（`src/middleware/error-handler.ts`）

```typescript
export const errorHandler = (err: Error, c: Context) => {
  if (err instanceof AppError) {
    return c.json({ error_code: err.code, message: err.message, details: err.details }, err.status)
  }
  logger.error({ err }, 'unhandled error')
  return c.json({ error_code: 'INTERNAL_ERROR', message: '伺服器內部錯誤' }, 500)
}
```
