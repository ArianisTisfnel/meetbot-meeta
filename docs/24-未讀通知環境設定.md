# 24 — 專案未讀通知圓點環境設定

> 🔒 **凍結快照**：記錄「專案卡未讀圓點」併入當下需要動手做的事。讀完即退場，不必回頭維護。
> 沒有列到的項目 = **不用做**。

拉到這份 code 之後，依序照做。全部大約 2 分鐘。

---

## 一、要不要 `npm install`？

**不用。** 這次沒有新增任何套件。圓點是純 CSS，明細對話框沿用既有的 `dialog.tsx`。

---

## 二、要不要 `npx prisma db push`？

**要，這次一定要跑。** 新增了一張表 `app.project_read_states`（記錄每個人在每個專案
「看到哪裡了」）。不跑的話後端一列專案就會炸 `relation "app.project_read_states" does not exist`。

```bash
# 1. 確認 Postgres 起著（本機 Docker 的話）
docker compose up -d postgres

# 2. 同步 schema（純新增一張表，不會動到任何既有資料）
cd backend
npx prisma db push
```

跑完會看到 `Your database is now in sync with your Prisma schema.`。

⚠️ 需要 `.env` 裡有 `DIRECT_URL`（Prisma CLI 走 session pooler）。這個變數在 22、23 就有了，
沒改過的話不用動。

**要不要重跑 `npx prisma generate`？** `db push` 會自動跑，不用另外下。

---

## 三、要不要加環境變數？

**不用。** 這次沒有任何新的環境變數，`.env` 完全不必動。

---

## 四、要不要裝東西（ngrok / Docker / 外部服務）？

**不用。** 未讀數全部從自家 DB 算出來，不碰 Recall、Dify、Google Calendar。

---

## 五、跑起來之後看得到什麼

**紅點掛在「哪裡有變動」的那個分頁上。**

1. 進 **我的專案**，有更新的專案卡**右上角**浮一顆紅點，數字是各分頁相加（超過 99 顯示 `99+`）。
2. 點紅點跳出明細，用 `1. 2. 3. 4.` 列出來，每則標了屬於哪個分頁；待回覆的會議排最前面。
3. 點進專案，**分頁列上各自帶紅點**：有人上傳資料 →「資料」亮；有人排會議 →「行事曆」亮；
   成員異動 →「成員」亮；專案改名 →「歷史」亮。
4. **切到哪個分頁就只清哪一顆**，其他分頁還沒看的不會被連坐蓋掉。
5. **待回覆的會議不會因為打開分頁而消失**——那是待辦不是消息，要真的在行事曆按了
   出席／不出席才會少一顆。明細對話框下方有「去行事曆回覆出席 →」直接帶過去。

各分頁相加恆等於卡片上那顆的數字，不會兜不攏。

### 自己驗一次（要兩個帳號）

| 步驟 | 做的人 | 預期 |
|------|--------|------|
| 1 | A 建專案，邀 B 加入 | — |
| 2 | A 上傳一份資料 | B 的專案卡出現紅點 `1`；進去後「資料」分頁亮 `1` |
| 3 | A 排一場會議、把 B 加為與會者 | B 的卡片變 `3`：「資料」`1`、「行事曆」`2`（1 則排會議動態 + 1 場待回覆） |
| 4 | B 點「資料」分頁 | 資料的紅點消失，行事曆的 `2` **還在** |
| 5 | B 點「行事曆」分頁 | 行事曆剩 `1`（動態清掉，待回覆還在） |
| 6 | B 按「出席」 | 全部歸零 |

> 紅點每 60 秒更新一次，切回瀏覽器分頁時也會重抓。等不及就重新整理。

## 七、如果你在 2026-09-02 之前就拉過這個分支

早一版的 `project_read_states` 是「專案層級已讀」（唯一鍵只有 `project_id + vexa_user_id`），
後來改成「分頁層級已讀」，多了 `section` 欄位。**表裡已經有資料的話 `db push` 會擋下來**：

```
Added the required column `section` ... There are N rows in this table
```

不要用 `--force-reset`（那會清掉整個資料庫）。舊語意「整個專案在 T 已讀」等價於
「五個分頁都在 T 已讀」，所以一列展成五列即可，無損：

```sql
BEGIN;
CREATE TYPE app.project_section AS ENUM ('MATERIALS','MEETINGS','CALENDAR','MEMBERS','HISTORY');
ALTER TABLE app.project_read_states ADD COLUMN section app.project_section;
UPDATE app.project_read_states SET section = 'MATERIALS' WHERE section IS NULL;
-- 舊唯一鍵必須先拿掉：展開後同一組 (project, user) 會有五列
DROP INDEX app.project_read_states_project_id_vexa_user_id_key;
INSERT INTO app.project_read_states
  (id, project_id, vexa_user_id, section, last_read_at, created_at, updated_at)
SELECT gen_random_uuid(), r.project_id, r.vexa_user_id, s.section, r.last_read_at, r.created_at, r.updated_at
FROM app.project_read_states r
CROSS JOIN unnest(ARRAY['MEETINGS','CALENDAR','MEMBERS','HISTORY']::app.project_section[]) AS s(section)
WHERE r.section = 'MATERIALS';
ALTER TABLE app.project_read_states ALTER COLUMN section SET NOT NULL;
CREATE UNIQUE INDEX project_read_states_project_id_vexa_user_id_section_key
  ON app.project_read_states (project_id, vexa_user_id, section);
COMMIT;
```

跑完再 `npx prisma db push`，會回「in sync」。

**第一次拉這個分支的人不必理這段**——表還不存在，`db push` 直接建好。
