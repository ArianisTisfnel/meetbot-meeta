# 蜜塔語音延遲：根因分析、官方架構比較與改造方案

> 📋 團隊報告 · 2026-07-09
> 範圍：語音「接收 → 回覆」全鏈路（Recall.ai 路徑）。聊天室問答、摘要、Vexa 路徑不在本次範圍。
> 網頁版：https://claude.ai/code/artifact/4312f4af-d873-4962-ad20-e761d84c9ae3
> 實作細節：[docs/15-OutputMedia-即時語音Agent-實作方案.md](15-OutputMedia-即時語音Agent-實作方案.md)

## TL;DR

**延遲的根因不在後端邏輯、也不在 Dify，而是 STT 模式選錯了。**我們用的 `recallai_streaming` + `prioritize_accuracy`（中文唯一選項）底層是**非即時的批次轉錄模型**——官方文件明載其即時事件「通常延遲 3–10 分鐘」，且幾乎不發 partial。文字晚到，喚醒、ack、回答整條鏈全部被拖著等。

解法是採用 Recall 官方參考架構（Output Media 網頁 + 音訊串流），分兩階段落地；**方案 A 只換「耳朵和嘴巴」，喚醒邏輯與 Dify 大腦一行不動**，預估把喚醒 ack 從分鐘級壓到 1 秒內。

### 名詞解釋（讀報告前先看這五個）

| 名詞 | 說明 |
|------|------|
| `recallai_streaming` | Recall.ai **自家的語音轉文字（STT）服務**。我們派 bot 進會議時指定用它轉錄，轉好的文字再經 webhook 送到我們後端——我們自己從頭到尾沒碰過聲音。 |
| 兩種模式 | 這個 STT 二選一：`prioritize_low_latency`（求快：講完 1–3 秒給文字，但**只支援英文**）和 `prioritize_accuracy`（求準：支援中文，但背後是「先錄下來、事後整批處理」的非即時模型，「即時」事件實際會晚好幾分鐘）。喚醒詞「蜜塔」是中文，只能選後者——這就是延遲源頭。 |
| partial（未定稿） | 串流 STT 會發兩種文字事件：**partial** 是「話講到一半就先推送的草稿」（幾百毫秒就到，內容可能還會變），**final** 是「一句話講完、確定不改」的定稿（要等講完＋停頓判定，慢 1.5–3 秒）。我們的快速喚醒靠 partial：草稿裡一出現「蜜塔」就先回「我收到了」。但 accuracy 模式**幾乎不發 partial**，機制整個失效。 |
| ack（確認回應） | 聽到喚醒詞後蜜塔先說的「好的，我收到了，正在查詢資料」。作用是讓使用者知道「有聽到」，跟後面查資料的速度是兩回事。 |
| Output Media 網頁 | Recall 的功能：bot 是雲端一台跑 Chrome 的機器，開啟後它會載入**一個我們自己寫的網頁**——網頁畫面＝bot 的鏡頭（與會者看到的蜜塔視訊格）、網頁播的聲音＝bot 的嘴巴（直接進會議，不用上傳 mp3）、網頁還能用 `getUserMedia` 收到會議即時音訊＝bot 的耳朵。網頁裡的 JavaScript 可開 WebSocket 連回後端，整條路變成即時串流——這是官方 demo 快的全部秘密。 |

## 01 前因：我們觀察到什麼

- 與會者說「蜜塔」之後，**「我收到了」的確認語音很晚才出現**，久到使用者以為沒收到而重問。
- 整體語音互動有明顯延遲感，體感遠慢於設計預期（partial 快速喚醒的設計目標是 ~1 秒 ack）。
- 後端早已留下線索：程式註解記錄「`prioritize_accuracy` 模式實測幾乎不發 partial」（`recall-adapter.ts:61`），為此還加了 `sawPartial` 診斷欄位。

一開始懷疑過喚醒比對邏輯與 Dify 查詢速度，但兩者都經查證排除：喚醒是 regex 比對（微秒級）；Dify 只影響「答案」那段，不影響「有反應」的 ack。

## 02 現況：我們的「接收 → 回覆」鏈路

### 喚醒 ACK 路徑（「我收到了」為什麼慢）

```
與會者說話          t = 0
  ↓
Recall 雲端 STT     ⚠️ 數十秒～數分鐘 ← 瓶頸
  （recallai_streaming / prioritize_accuracy，async 批次模型）
  ↓
Webhook 送達後端     ~0.1–0.5s（partial 幾乎不來，只有 final）
  ↓
喚醒比對             ~0ms（WAKE_WORD_REGEX＋待命窗／debounce）
  ↓
ACK 語音             ~1s（TTS 已預熱 → POST mp3 → 播放）
```

### 答案路徑（ack 之後）

```
問題定稿（等 final，同樣被 STT 卡）
  ↓
意圖分流             ~1–2s（chitchat / factual / context / hybrid）
  ↓
Dify RAG 查詢        ~15–20s
  ↓
TTS 產完整 mp3       ~1–3s（不能串流，要等整支）
  ↓
base64 上傳＋播放    ~0.5–1s
```

結構性問題一目瞭然：**每一站都是「批次」——等前一站整批做完才開始**。而第一站（STT）就是分鐘級，後面再快都沒有意義。

## 03 根因：prioritize_accuracy 根本不是即時模式

我們當初選 `prioritize_accuracy` 是被迫的：Recall 原生串流 STT 的低延遲模式**只支援英文**，中文喚醒詞「蜜塔」只能選 accuracy 模式。但官方文件寫明了代價：

> `prioritize_low_latency`：定稿後 1–3 秒送達，僅支援英文（`language_code: "en"`）。
> `prioritize_accuracy`：使用非即時（async）轉錄模型，即時端點的事件「**typically delayed by 3–10 minutes**」。
> — Recall.ai 官方文件〈Recall.ai Transcription〉

三個關鍵結論：

1. **「串流比對喚醒詞」我們早就做了。**`handlePartialSegment` 在 partial 出現「蜜塔」的瞬間就先說「我收到了」（TTS 也預熱過）。設計是對的——問題是 accuracy 模式**幾乎不發 partial**，final 又是分鐘級，整套快速喚醒機制形同虛設。
2. **不是「一句話講完才比對」的邏輯問題。**是「文字根本還沒送到我們手上」的資料源問題。
3. **修比對邏輯無濟於事；要換的是資料源**——換一個真正串流、又支援中文的音訊入口。

## 04 Recall 官方是怎麼做的（已讀原始碼確認）

我們把官方 [voice-agent-demo](https://github.com/recallai/voice-agent-demo) 的原始碼實際翻過（App.tsx、relay server、conversation config），並比對 [Output Media 文件](https://docs.recall.ai/docs/stream-media)與 [HeyGen avatar 範例](https://github.com/recallai/sample-apps/tree/main/bot_output_media_heygen_avatar)。官方架構：

```
與會者說話
  ↓ 毫秒級
Output Media 網頁（bot 瀏覽器跑我們的網頁，getUserMedia 直接收音）
  ↓ 毫秒級
WS relay（PCM16 雙向轉發，純管線無邏輯）
  ↓ 串流
OpenAI Realtime API（STT＋對話＋語音同一個模型內完成）
  ↓ 首音 ~0.5s
音訊 delta 串回網頁（邊生成邊播放，網頁聲音＝bot 聲音）
```

### 兩個必須對齊的事實（跟我們原本的認知不同）

1. **官方 demo 完全沒有用 transcript**——不管是 Recall 原生還是第三方轉錄。原始音訊直接進 OpenAI Realtime API，語音辨識在模型內部完成。這正是它快的原因：整條鏈只有「音訊串流進、音訊串流出」，沒有任何一站在等句子定稿。
2. **官方 demo 沒有做「知道在叫自己」。**它的設定是 `turn_detection: server_vad`——只要有人講話停頓就回答，來者不拒（它是測試 agent）。喚醒詞邏輯必須自己做；標準做法是 `create_response: false`（模型不自動開口）＋開啟 input transcription，對串流文字跑喚醒 regex，命中才觸發回覆。**我們現有的整套喚醒邏輯（regex、待命窗、debounce）可以原封不動搬過去用。**

### 逐項比較

| 環節 | 我們（現況） | Recall 官方參考模式 |
|------|------------|-------------------|
| 音訊怎麼進來 | 不碰音訊。等 Recall 雲端 STT 轉好文字，webhook 一句一句 POST 過來 | Output Media 網頁在 bot 瀏覽器內 `getUserMedia`，**毫秒級拿到原始音訊流** |
| STT | recallai_streaming（accuracy 模式）＝async 批次模型 🔴 分鐘級 | 音訊直進 OpenAI Realtime，模型內建串流辨識 🟢 數百 ms |
| 「知道在叫自己」 | WAKE_WORD_REGEX 比對 webhook 文字（邏輯正確，被資料源拖垮） | demo 未實作（VAD 停頓就答）；需自行做 gating，**可沿用我們的 regex 邏輯** |
| 回覆怎麼出去 | 文字 → 產完整 mp3 → base64 POST → 播放 🟡 批次 2–4s | 音訊 delta 串流回網頁邊收邊播 🟢 首音 ~0.5s |
| 插話讓路（barge-in） | 靠 STT 事件觸發 → 也被分鐘級延遲拖垮 | 原生支援：`conversation.interrupted` → 播放器即停＋取消生成 |
| 喚醒 ack 體感 | 🔴 數十秒～分鐘 | 🟢 < 1 秒 |

## 05 改造方案：兩階段落地

兩個方案共用同一套基礎設施（Output Media 網頁＋後端 WS relay）。**建議先做方案 A**：改動面最小、風險最低、可完整回退，而且直接解決本次的延遲問題。

### 方案 A：換耳朵和嘴巴，大腦不動 ⭐ 建議先做

```
網頁收音（getUserMedia → PCM16）          毫秒級
  ↓
WS → 後端 relay → gpt-4o-mini-transcribe   partial 數百 ms（支援中文）
  ↓
喚醒邏輯（regex／待命窗／debounce 原封不動搬進 relay）
  ↓
即時 ACK（預錄 PCM 直接推流，零合成、零上傳）  ~0.5s
  ↓
答案：resolveAnswer＋Dify 不動 → streaming TTS 邊合成邊播
                                          Dify 時間＋首音 ~0.5s
```

插話讓路：relay 在播放中偵測到新語音 delta → 推 stop 指令給網頁 → **0.5 秒內靜音**。

### 方案 B（演進）：gpt-realtime 語音對語音（A 驗證後評估）

全套官方模式：音訊直進 `gpt-realtime`，`create_response: false` 做喚醒 gating，Dify 檢索包成 function tool——模型口頭 ack 後呼叫工具、拿到結果再唸答案，追問體驗最自然。代價是音訊 token 持續計費、改動面較大，等 A 的基礎設施跑穩再上。

### 實作項目（方案 A）

| # | 項目 | 位置 | 內容 |
|---|------|------|------|
| 1 | Bot 加掛網頁 | `recall-adapter.ts` | join payload 加 `output_media.camera = webpage`（帶 meetingInstanceId＋簽名 token）；recording_config 保留（摘要與聊天室 webhook 不動） |
| 2 | 後端 WS relay | `backend/src/agent/`（新） | `/ws/agent`：橋接網頁 ⇄ OpenAI transcription session；內嵌喚醒邏輯；ack 預錄 PCM；答案走 streaming TTS 轉發 |
| 3 | Agent 網頁 | `frontend/app/agent/`（新） | 收音（PCM16 24kHz → WS）＋串流播放；官方 demo 的 wavtools 為 MIT 授權可直接沿用；順勢做成蜜塔的視覺形象（聆聽／查詢／回答狀態） |
| 4 | 開關與回退 | `env.ts`、`.env` | 新增 `AGENT_MODE`／`AGENT_PAGE_URL`；off 時完全走現行路徑，webhook＋mp3 保留為 fallback |
| 5 | 完全不動的部分 | — | resolveAnswer／意圖分流／Dify、聊天室問答、會後摘要、Vexa failover 路徑 |

### 驗收指標（實際開會量測）

- 說「蜜塔」→ 聽到 ack：**< 1.5 秒**（現況：數十秒～分鐘）
- 問題說完 → 答案開始播放：**< Dify 時間 + 2 秒**（不再等整支 mp3）
- 蜜塔講話中插話 → 聲音停止：**< 0.5 秒**
- `AGENT_MODE=off` 重啟後，行為與現行版本完全一致（回退驗證）

### 風險與已知限制

- **網頁存活**：bot 瀏覽器當掉＝蜜塔失聰失聲 → relay 心跳偵測，斷線退回 webhook＋mp3 fallback。
- **成本**：全程串流轉錄＋TTS，一小時會議約 60 分鐘 STT 用量；遠低於方案 B 的 realtime 音訊 token。
- **多進程限制不變**：relay 狀態在記憶體，維持 PM2 fork mode 單進程。
- **Vexa 路徑不受惠**：failover 進 Vexa 時仍是舊行為（Vexa 用它自己的 STT）。

> 建議動工順序：項目 1 → 3 → 2——先讓 bot 帶著網頁進會議、確認收得到音訊，這一步通了之後剩下的都是純後端工作。

## 06 聊天室不受影響的確認

> 常見疑問：「webhook 不是跟聊天室有關嗎？改語音架構會不會弄壞聊天室？」——不會。
> 聊天室和語音雖然走**同一條 webhook**，卻是**兩種不同的事件**，方案 A 只改語音那種。

Webhook（`/webhooks/recall`）收三種事件，在 `dispatchRecallEvent` 分流：

| 事件 | 用途 | 方案 A 的處置 |
|------|------|--------------|
| `transcript.data` / `transcript.partial_data` | **語音**逐字稿（喚醒詞來源） | 喚醒改由 agent 網頁的串流音訊驅動；webhook 這兩種事件只留著寫逐字稿 |
| `participant_events.chat_message` | **聊天室**訊息 | **完全不動** |

聊天室安全的理由——整條路徑從頭到尾不經過任何被改動的環節：

1. **進**：聊天室打「蜜塔 …」→ `participant_events.chat_message` webhook → `handleChatMessage` 比對喚醒詞 → `resolveAnswer`。這是「參與者事件」，跟 STT／transcript provider 無關——打字本來就是即時的，從來沒有延遲問題，也不受換 STT 影響。
2. **出**：蜜塔回聊天室走 `POST /send_chat_message/` API（`sendChat`），跟 Output Media、語音輸出是兩條路。
3. **周邊**：歡迎訊息、被打斷時「完整回覆放聊天室」、`chatLog` 併入會後逐字稿——全部走上面兩條，不受影響。

方案 A 對 bot 建立 payload 是「**加**一個 `output_media` 欄位」，原本的 `recording_config`（含 webhook 的 `realtime_endpoints`）原封不動保留。

⚠️ 實作時唯一要確實做到的：agent 模式下，webhook 的 `transcript.data` 只能**寫逐字稿**、不能再觸發喚醒——accuracy 模式的 transcript 是分鐘級延遲，不關掉的話，同一句「蜜塔」會在新路徑答完幾分鐘後，被晚到的 webhook 事件**再觸發一次、重複回答**。這正是實作項目 4（`AGENT_MODE` 開關）要停用「webhook 語音喚醒路徑」的原因；聊天室 handler 與此開關無關，繼續全速運作。

## 07 後續改進路線（Roadmap）

> 現階段目標只有一個：**用方案 A 解決延遲**。語言範圍先以**繁體中文＋英文**（含中英夾雜）為主。
> 以下是架構到位後「換模型就能升級」的未來改進點——方案 A 的 relay 是模型無關的，
> STT／TTS 都只是端點置換，不需要再動架構。

### 現在做

| 項目 | 內容 |
|------|------|
| 方案 A | Output Media 網頁＋後端 relay，STT 用 OpenAI `gpt-4o-mini-transcribe`、TTS 用 OpenAI streaming TTS。目標：喚醒 ack < 1.5 秒 |
| 語言範圍 | 繁體中文＋英文為主（喚醒詞「蜜塔」與中英夾雜會議） |


### 未來改進點

**① STT 換成 Taiwan Tongues ASR CE（開源自架）**

- 數產署開源 ASR（[GitHub](https://github.com/adi-gov-tw/Taiwan-Tongues-ASR-CE)，MIT 授權，台灣大哥大維護），支援國、台、客、英**混合辨識**。
- 內建**即時辨識 WebSocket API**（`/ws/v1/transcript`）：輸入 PCM Int16 / mono / 16kHz 分塊串流；開 `enableTransient=1` 會在講話中途回傳未定稿結果（`final: 0`）——**與方案 A 需要的 partial 機制完全同構**，relay 只需把 OpenAI 端點換成它，喚醒邏輯零改動（僅需 24kHz→16kHz 重採樣）。
- 代價：需自架 GPU（推論 VRAM 10GB+，如 RTX 3080）；Whisper 系分塊串流，partial 延遲估計比 OpenAI 稍慢（仍為秒級）；會議情境的辨識品質需 PoC 驗證。
- 附帶效益：OpenAI 版可作為對照組，延遲／準確率比較數據可直接用於競賽文件；蜜塔的喚醒詞誤轉容錯（蜜塔→米塔／蜜桃）與會議語料可回饋開源生態（競賽加分項）。

**② TTS 換成 BreezyVoice（開源自架）**

- 聯發創新基地的台灣口音語音合成（[GitHub](https://github.com/mtkresearch/BreezyVoice)，Apache 2.0），輸入文字＋參考音色樣本即可合成。
- 融入方式：**ack 固定台詞用它預先錄製**（台灣口音、音色一致，播放時零合成延遲）；**答案採按句切段合成**（合成第一句時開始播放，後續邊播邊合成）補足它沒有串流合成的限制。
- 代價：需 GPU；README 未提供 RTF／推論速度數據，需實測。

**③ 台語（及客語）會議支援**

- Taiwan Tongues 原生支援台、客語，改進點 ① 完成後**不需額外架構工作**，屬模型能力的自然延伸。
- 定位為差異化亮點：目前市面上的會議 bot 沒有支援台語會議的產品。
