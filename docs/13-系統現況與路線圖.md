# 🟢 系統現況與路線圖（活文件）

> 最後更新：2026-07-06 ｜ 給團隊成員與 AI 助手快速對齊用。

## 一句話介紹

**蜜塔（Meeta）**：加入 Google Meet 的 AI 會議助理——叫她就答（專案知識庫 RAG）、不叫她也會看場合主動補充、冷場會破冰，散會自動產出摘要與逐字稿。

---

## 架構總圖

```
Google Meet
   │  bot 進場/錄音/STT/播音 —— 全由 Recall.ai 雲端 bot 處理
   ▼
【Recall.ai】(主 provider；Vexa 為 failover 備援，被 reCAPTCHA 擋死已退居二線)
   │  realtime webhook：逐字稿(final+partial)/聊天訊息 → ngrok → 本機後端
   ▼
Hono 後端（Node.js）── Session 引擎（in-memory，單進程）
   ├─ 喚醒詞問答：partial 快速確認(~1s) → 意圖分流 → 回答（語音）
   │     分流：factual→Dify RAG／context→LLM+逐字稿／hybrid→先檢索後合成
   ├─ 主動插話：EOU 模型判斷「講完了」→ Gemini 決策「該不該插話」
   │     → 沉默時語音輸出、有人講話貼聊天室 💡
   ├─ 沉默破冰：全場靜默 40s → 開場用罐頭引導／會中用 LLM 總結+拋問題
   ├─ 讓路 barge-in：蜜塔說話中有人開口(≥4字) → 停止語音、內容轉聊天室
   │     「閉嘴/安靜」等停止指令直接生效且不轉貼
   └─ 會議結束 → 逐字稿(語音+聊天合併) → Supabase Storage → Dify 摘要
   ▼
【Dify】知識庫 RAG + 會議摘要 ｜【Gemini】決策/意見問答（免費額度）
【Supabase】DB(app schema) + Storage(逐字稿檔) ｜【OpenAI】TTS(蜜塔的聲音)
```

Next.js 前端：專案/知識庫/成員權限/會議頁（即時逐字稿、摘要、會後逐字稿）。

## 使用的外部服務與 Open Source

| 名稱 | 角色 | 使用時機 |
|------|------|---------|
| **Recall.ai**（付費） | 進會議、逐字稿、播音的基礎設施 | 永遠 |
| **Dify**（免費額度） | 知識庫 RAG、會議摘要 workflow | 事實型問答、會後摘要 |
| **Gemini API**（免費額度） | 插話決策、意見型/脈絡型問答、破冰文案 | `GEMINI_API_KEY` 設定時優先於 Anthropic |
| **LiveKit turn-detector**（開源模型，Apache-2.0） | 判斷「一句話講完了嗎」（EOU），插話時機層 | 已上線；本機 ONNX 推論 ~40ms，`backend/models/` |
| **OpenCC (opencc-js)** | 簡體→繁體（台灣用語）確定性轉換 | 逐字稿/摘要/回答全部出口 |
| **OpenAI TTS**（付費，量小） | 蜜塔語音（text→mp3） | 有快取+進場預熱，固定台詞免重複合成 |
| **Vexa**（自架） | 備援 provider | Recall 失敗時 failover（實務上進不了 Meet） |

評估過**不採用**：joinly（互動層綁死自己的瀏覽器 bot，進 Meet 同樣被 reCAPTCHA 擋）、DeepPavlov（LLM 分流已覆蓋）、AutoGen（單 bot 用不到多代理框架）、SpeechBrain/Pipecat（音訊層工具，Recall 已代勞，見 P5）。

## 已完成功能與實作邏輯

### 1. 進場與 failover
`BOT_PRIMARY_PROVIDER=recall`（env 可切）。FailoverProvider 先派主 provider，被擋/逾時才派備援；join 後所有操作委派給建立 session 的 adapter，上層無 provider 分支。
→ `backend/src/provider/`（types / recall-adapter / vexa-adapter / failover-provider / index）

### 2. 喚醒詞問答（體感 ~1 秒回應）
- **partial 快速確認**：訂閱 Recall `transcript.partial_data`（講到一半就到），偵測到喚醒詞立即播預熱好的「我收到了」；問題內容等定稿段落，`partialAckAt` 一次性銜接避免重複開場白
- **喚醒詞容錯**：`[蜜密祕秘迷米咪][塔搭達]|小幫手|Me{1,2}ta|Mita`（STT 實測會把「蜜塔」轉成「米塔」）；「叫名字→停頓→問問題」有 8 秒待命窗
- **意圖分流**：問題先經 Gemini 三分類——factual→Dify RAG；context（你覺得如何）→LLM+近期逐字稿與聊天室訊息（純打字會議也有脈絡可用）；hybrid→先 Dify 檢索、再與對話脈絡合成。分類失敗回退 factual；接續型追問（「那X呢」）規則上偏 factual（2026-07-07 實測「那 Beta 呢」誤分 context 修正）；評估資料內容的意見題偏 hybrid（同日實測修正）
→ `backend/src/sessions/wake-word-detector.ts`

### 3. 主動插話（不叫名字也會補充）
三層：**時機層**（LiveKit EOU 模型：靜默 1s 先問「講完了嗎」，講完提早評估；模型不可用退回 2.5s 停頓計時）→ **決策層**（Gemini 判斷：明確問題？資料答得出？沒人在答？＋90s 冷卻等硬防護）→ **執行層**（現場沉默→語音「我補充一下…」；有人講話→聊天室 💡）。
檢索沒中（哨兵句）或空答案 → 該次插話放棄不投遞（冷卻照計，避免同題連環觸發）。
→ `backend/src/sessions/interjection.ts`、`backend/src/lib/eou.ts`；prompt 集中在 `interjection-prompts.ts`，改 prompt 前後先跑 `backend/scripts/eval-interjection.ts` 評測（16 劇本、支援 A/B 變體）

### 4. 沉默破冰
全場靜默 40s（`ICEBREAKER_SILENCE_MS`）→ 開場（幾乎沒人講過話）用罐頭引導；會議中用 LLM 總結進度＋拋問題。語音輸出、5 分鐘冷卻、任何活動重置計時；LLM 失敗或回空 → 該輪跳過、監看不中斷；生成期間有人開口 → 放棄本輪（不撞提問者）；同一段沉默只破冰一次，需有人再發言後的新沉默才會再觸發。
→ `interjection.ts` 的 `startIcebreaker`/`fireIcebreaker`（prompt 同樣在 `interjection-prompts.ts`）

### 5. 讓路（barge-in）
蜜塔說話中有人開口（≥4 字，過濾「嗯嗯」附和）→ 立即停止（Recall `DELETE output_audio`）、被打斷的回答轉貼聊天室；「閉嘴/安靜/停」等停止指令再短也生效且不轉貼。查詢期間被打斷（`bargeEpoch` 偵測）→ 答案直接走聊天室。
→ `wake-word-detector.ts` 的 `handleBargeIn`

### 6. 逐字稿與摘要
- 語音 segments（含蜜塔自己的語音回覆）＋聊天訊息（含蜜塔的 💡，標「（聊天室）」）按時間合併 → 純文字存 Supabase Storage → Dify workflow 產摘要/重點主題/決議/待辦
- 全出口強制繁體中文（OpenCC cn→twp）
→ `backend/src/sessions/summary.service.ts`、`backend/src/provider/normalize.ts`、`backend/src/lib/zh.ts`

### 7. 可觀測性
pino log 同時寫 `backend/logs/backend.log`；喚醒命中/意圖分類/插話決策/破冰/讓路/答案送出全都有明確 log 行，可事後重建會議時序。

## 環境開關速查（backend/.env）

```
BOT_PRIMARY_PROVIDER=recall      # 主 provider（recall/vexa）
INTERJECTION_ENABLED=true        # 主動插話
INTERJECTION_TURN_DETECTOR=livekit  # 時機層（silence/livekit）
ICEBREAKER_ENABLED=true          # 沉默破冰（40s，冷卻 5min）
GEMINI_API_KEY=...               # 設了就優先走 Gemini（免費）
RECALL_WEBHOOK_URL=...           # ngrok 公開網址（realtime 必要）
```

單元測試：`npx vitest run`（根目錄）。後端 log：`backend/logs/backend.log`。
