## B. 回覆功能標籤 ✅ 完成

蜜塔的聊天室訊息一律加上功能標籤，可歸因到觸發它的子系統：

| 標籤 | 代表 |
|---|---|
| 【資料檢索】 | 查了 Dify 知識庫（RAG） |
| 【會議記錄】 | 只看本場逐字稿／聊天記錄，沒查知識庫 |
| 【閒聊】 | 純 LLM 寒暄，完全沒碰知識庫與逐字稿 |
| 【冷場插話】 | 沒人叫她，插話決策層判斷該補充 |
| 【破冰】 | 全場靜默觸發 |
| 【收到】 | 收到發言的即時確認（不預設對方在提問） |
| 【接續回覆】 | 被打斷後改用文字補完 |
| 【錯誤】 | 查詢失敗 |

三個設計約束：

1. **只加在聊天室文字，語音永遠不唸標籤**——唸「資料檢索」違反人設的通道禮儀。
2. **不進 chatLog、不進插話對話窗**。標籤是給人看的除錯前綴，混進去會污染決策層的
   LLM 輸入，也會出現在會後逐字稿與摘要裡。實作上只在呼叫 provider 那一刻才前綴。
3. **可關**：`REPLY_TAGS=off`（預設 `on`）。正式對外會議不想露出除錯資訊時關掉。

### 順手修掉的兩個相關病灶

- **開頭的逗號**（回報裡貼的「,可以告訴我…」）：喚醒詞剝除後的清標規則只清全形
  `，。！？、…`，但 AGENT_MODE 走 OpenAI 轉錄輸出的是**半形** `,` `.` `?`。
  這個逗號不只出現在覆誦，還會一路帶進 Dify 的檢索查詢字串。已改成全形半形都清。
- **ack 誤宣稱「正在查詢資料中」**：這句在意圖分類**之前**就送出，此時根本還不知道
  會走 RAG／逐字稿／閒聊哪條路。已改成中性措辭（「稍等一下～」），實際走哪條由答案
  自己的標籤說明。語音的「我收到了，正在查詢資料」同樣改成中性。

### 澄清一個誤判

回報 A.2 說「跟蜜塔打招呼，她會去資料庫查詢『你好』」——**分類器沒有壞**。
用 `eval-meeting.ts --intent` 驗證，「你好」「在嗎」「你是誰」全部正確分類為 chitchat，
根本沒送 Dify。造成那個印象的純粹是上面那句誤導的 ack 文案，已修。

## A. 語意層 🟡 部分完成

### 已完成：定址判斷（「這句是不是在對蜜塔說話」）

原本 `WAKE_WORD_REGEX` 是純字串比對，只要出現「蜜塔」就觸發（回報 A.1）。
改成三態判斷（`backend/src/sessions/addressing.ts`）：

| 句型 | 判定 | 成本 |
|---|---|---|
| 句首呼喚「蜜塔，X」「蜜塔 X」 | 直接派發 | 零 LLM、零延遲 |
| 只叫名字「蜜塔」 | 開待命窗等下一段 | 零 LLM |
| 非呼喚句型「蜜塔這個功能…」「我覺得蜜塔…」 | 送語意裁決 | 一次便宜的 LLM 呼叫 |

關鍵分界是**喚醒詞後面有沒有停頓標點**：呼喚語必然有（STT 也確實會插逗號——
回報裡那個「,可以告訴我」就是證據），談論則直接黏名詞（「蜜塔這個功能」）。
單看位置不夠：「蜜塔剛才說截止日是六月三十號對吧」也在句首，但那是在向他人求證。

語意裁決在 `backend/src/sessions/response-policy.ts`
（原 `ADDRESS_ARBITER_SYSTEM`；2026-07-29 已併入 `TURN_DECISION_SYSTEM`，見下）。
效果：回報 A.1 的四個誤觸發案例全部改為正確沉默。

**失敗退回策略很重要**：裁決呼叫失敗（Gemini 429）一律**退回舊行為照常回答**，
不可當成「沒在叫我」——否則額度一枯竭蜜塔就對所有非逗號句型全聾。

### A.3 連續追問（2026-07-29 已實作）

**原本的問題**：沒喊名字的追問只能靠 8 秒待命窗，接不上「那名額有限制嗎」這種
第二、三輪追問。正解是把定址併進插話決策層——那一層本來就在每輪話結束時看同一份
rolling window，問的是高度重疊的問題。

**已拍板的三點設計**，全部照做：

1. **每輪一次 LLM 呼叫同時產出 {定址, 意圖, 插話決策}**，取代 `classifyIntent`
   與 `INTERJECTION_DECISION_SYSTEM` 兩次高度重疊的呼叫。額度不增反減。
2. **保留正則快速路徑。** 句首呼喚仍立即 ack，維持 agent 模式的秒級回應。
3. **`WAKE_PENDING_MS` 待命窗退役。**

**落地的樣子**：

| 層 | 檔案 | 負責什麼 |
|---|---|---|
| 規則 | `addressing.ts` | 句首呼喚／叫停直接定案（零成本）；其餘標成 `ambiguous`（有喊名字）或 `followup-candidate`（沒喊名字、對話串還開著）交上去 |
| 語意 | `interjection-prompts.ts` `TURN_DECISION_SYSTEM` ＋ `response-policy.ts` `decideTurn` | 一次呼叫回 `{addressed, question, intent, interject}` |
| 執行 | `wake-word-detector.ts` / `interjection.ts` | `addressed=address` → 當喚醒問答回答（追問走這條）；否則才看 `interject` |

實作時有四件事和原構想不同，都值得記著：

1. **追問的判定放在 turn 結束（`interjection.ts`），不是收到 segment 就判。**
   一輪話常被 STT 切成好幾段，逐段判會把「每輪一次呼叫」變成每段一次。
   代價是追問比句首呼喚慢一個 `INTERJECTION_TURN_SILENCE_MS`（2.5 秒）——可接受，
   因為追問沒有 partial ack 可搶，本來就走完整流程。
2. **`WAKE_PENDING_MS` 換成 `FOLLOWUP_WINDOW_MS`（90 秒），角色完全不同。**
   舊的是**判準**（窗內就當問題 → 只接得住「叫名字→停頓→問題」）；
   新的只是**成本閘門**（擋掉蜜塔沒參與過的對話，免得整場每句都送去問），判準交給語意層。
   所以可以放寬到 90 秒——判錯的成本由語意層承擔，不是由這個數字承擔。
   叫停會把它歸零：叫停就是叫停，不是換個方式繼續問。
3. **呼叫失敗的退回方向，兩條路相反，不可統一。**
   有喊名字（句中提及）→ 退回照常回答（原本的紅線：判不出來不等於沒在叫我）。
   沒喊名字（追問候選）→ 退回**安靜**。這裡若也退回照常回答，額度一枯竭蜜塔就會把
   會議裡每一句話都當成在問她——那是災難等級的誤觸發，比全聾嚴重得多。
4. **「只剩喚醒詞的 question」要在解析層擋掉。**
   實測：對話窗是「[Arianis] 蜜塔」＋「[小華] 我先去倒杯水」時，模型判 `address`
   並把前一則的「蜜塔」當成本輪要回答的問題 → 有人喊一聲名字、別人接著講不相干的事，
   蜜塔就拿「蜜塔」兩個字去查知識庫。prompt 已寫明「question 一定要取自最後一則」，
   另外在 `parseTurnDecision` 加了結構性的第二道防線（放解析層，線上與離線評測才會一起擋住）。

**A.4（多人會議不知道在回應誰）** 是**上游能力被換掉**，不是語意層問題：

所以「👂 收到**的**問題」少了人名不是 bug，是這條路徑拿不到人名。調查結果：

- **OpenAI 這條走不通**：`gpt-4o-transcribe-diarize` 官方明載 Realtime API 不支援，

- **Recall 這條走得通**：即時 webhook 支援 `participant_events.speech_on`/`speech_off`，

  而 agent relay 的 `elapsedSec()` 正好是同一個座標系。
  `recall-adapter.ts` 已經在訂閱 realtime 事件，只要多訂這兩個，在 session 維護
  「某時刻誰在講話」的時間軸，用 segment 的 `startTime` 反查名字即可。

**2026-07-29 已實作**（`backend/src/agent/speaker-timeline.ts`）。實作時改了兩處原始構想：

1. **不用 `timestamp.relative`，改用 epoch ms。** relative 的原點是 Recall 錄製起點，
   `elapsedSec()` 的原點是 `anchorMs`（admitted 時刻），兩者不保證同刻——原構想說的
   「同一個座標系」並不成立。寫入端改用 `timestamp.absolute`（沒有才退回收到當下），
   讀取端用 `Date.now()`，對齊問題整個消失。
2. **不是點查詢，是回看窗查詢。** agent-relay 的 segment `startTime` 是**轉錄完成**時
   才取的 `elapsedSec()`，不是開口時刻；等定稿事件到達時講者早已 speech_off，
   點查詢必然落空。改成查 [at-15s, at] 窗內誰講最久。

## 順帶修掉的潛伏 bug：Gemini 3.x 拒收 thinkingBudget

`lib/llm.ts` 原本**無條件**送 `thinkingConfig: { thinkingBudget: 0 }`。
這在 Gemini 2.5 系列是必要的（不關掉，思考 token 會吃光 maxOutputTokens 導致空回覆），
但 **Gemini 3.x 直接以 HTTP 400 "Request contains an invalid argument" 拒收**，
而且 3.x 預設就不思考（實測 `thoughtsTokenCount=0`），根本不需要關。

觸發條件：`GEMINI_INTERJECTION_MODEL` 的預設值正是 3.x 的 `gemini-flash-lite-latest`，
而 llm.ts 是「用 interjection key 就同時換 interjection model」。所以**只要一設定
`GEMINI_INTERJECTION_API_KEY`**（`.env.example` 與文件都建議設，用來隔離額度），
插話決策／沉默破冰／定址裁決會同時全部 400 陣亡，症狀只是「蜜塔忽然安靜了」，
錯誤只寫在 warn log 裡。

目前 `.env` 的 `GEMINI_INTERJECTION_API_KEY` 是**設了但留空**，所以走的是
`GEMINI_API_KEY` + 預設 `gemini-2.5-flash`，功能正常——這個 bug 一直沒被引爆。

已修：`buildGeminiGenerationConfig()` 依模型世代分流，並加上單元測試鎖住。
