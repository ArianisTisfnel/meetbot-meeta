## B. 回覆功能標籤 ✅ 完成

蜜塔的聊天室訊息一律加上功能標籤，可歸因到觸發它的子系統：

| 標籤 | 代表 |
|---|---|
| 【資料檢索】 | 查了 Dify 知識庫（RAG） |
| 【會議記錄】 | 只看本場逐字稿／聊天記錄，沒查知識庫 |
| 【閒聊】 | 純 LLM 寒暄，完全沒碰知識庫與逐字稿 |
| 【冷場插話】 | 沒人叫她，插話決策層判斷該補充 |
| 【破冰】 | 全場靜默觸發 |
| 【收到提問】 | 收到問題的即時確認 |
| 【接續回覆】 | 被打斷後改用文字補完 |
| 【錯誤】 | 查詢失敗 |

三個設計約束：

1. **只加在聊天室文字，語音永遠不唸標籤**——唸「資料檢索」違反人設的通道禮儀。
2. **不進 chatLog、不進插話對話窗**。標籤是給人看的除錯前綴，混進去會污染決策層的
   LLM 輸入，也會出現在會後逐字稿與摘要裡。實作上只在呼叫 provider 那一刻才前綴。
3. **可關**：`REPLY_TAGS=off`（預設 `on`）。正式對外會議不想露出除錯資訊時關掉。

### 順手修掉的兩個相關病灶

- **開頭的逗號**（回報裡貼的「,可以告訴我…」）：喚醒詞剝除後的清標規則只清全形
  `，。！？、…`，但 AGENT_MODE 走 OpenAI 轉錄輸出的是**半形** `,` `.` `?`。
  這個逗號不只出現在覆誦，還會一路帶進 Dify 的檢索查詢字串。已改成全形半形都清。
- **ack 誤宣稱「正在查詢資料中」**：這句在意圖分類**之前**就送出，此時根本還不知道
  會走 RAG／逐字稿／閒聊哪條路。已改成中性措辭（「稍等一下～」），實際走哪條由答案
  自己的標籤說明。語音的「我收到了，正在查詢資料」同樣改成中性。

### 澄清一個誤判

回報 A.2 說「跟蜜塔打招呼，她會去資料庫查詢『你好』」——**分類器沒有壞**。
用 `eval-meeting.ts --intent` 驗證，「你好」「在嗎」「你是誰」全部正確分類為 chitchat，
根本沒送 Dify。造成那個印象的純粹是上面那句誤導的 ack 文案，已修。

## C. 離線模擬 ✅ 完成（兩層都做）

### C-1 劇本回歸測試：`backend/scripts/eval-meeting.ts`

拿手寫的會議劇本逐句跑「該不該回應／走哪條資料來源」，統計準確率。

```bash
cd backend
npx tsx scripts/eval-meeting.ts                           # 規則層，零 LLM 成本、秒回
npx tsx --env-file .env scripts/eval-meeting.ts --address # 加上語意定址裁決
npx tsx --env-file .env scripts/eval-meeting.ts --intent  # 加上意圖分流
```

劇本在 `scripts/meeting-scenarios.json`，目前 16 個劇本／40 個案例，涵蓋：
討論蜜塔本身、引用她說過的話、打招呼、連續追問、代詞指涉、對第三人說話、
STT 誤轉、半形標點、待命窗、debounce、純討論會議（誤觸發基準線）等。

**劇本一律手寫假設情境**，不指望真會議長案例——本專案真實會議場次少，
靠真會議累積覆蓋不了多少問題。

統計把「回歸失敗」（本來會過卻被改壞）與「已知缺口」（等語意層來修）分開，
只有前者會給非零退出碼，之後可直接掛進 CI。

### C-2 會議模擬器：`backend/scripts/simulate-meeting.ts`

用假 provider 把腳本餵進**完全真實的** session 管線（喚醒→意圖分流→Dify/逐字稿 QA→
插話/破冰），輸出蜜塔的動作時間軸。不開 Google Meet、不派 bot、不寫 DB。

```bash
cd backend
npx tsx --env-file .env scripts/simulate-meeting.ts
```

兩個支撐改動：

- `provider/index.ts` 加 `setBotProviderForSimulation()` 注入接縫（預設值是真 provider，
  正式流程永不呼叫）。
- `session-manager.ts` 把 live handlers 抽成 `buildLiveHandlers()`，模擬器用**完全相同**
  的接線，避免模擬行為跟線上悄悄分岔。

⚠️ `--speed` 只壓縮腳本播放，**不縮放** debounce(2s)／待命窗(8s)／破冰／插話冷卻，
也會把 LLM 呼叫擠在一起觸發免費層限流。實測 6x 下會憑空多出「查詢錯誤」與漏答。
**評估回應品質一律用預設 1x**，speed>1 只適合確認腳本跑得起來。

## A. 語意層 🟡 部分完成

### 已完成：定址判斷（「這句是不是在對蜜塔說話」）

原本 `WAKE_WORD_REGEX` 是純字串比對，只要出現「蜜塔」就觸發（回報 A.1）。
改成三態判斷（`backend/src/sessions/addressing.ts`）：

| 句型 | 判定 | 成本 |
|---|---|---|
| 句首呼喚「蜜塔，X」「蜜塔 X」 | 直接派發 | 零 LLM、零延遲 |
| 只叫名字「蜜塔」 | 開待命窗等下一段 | 零 LLM |
| 非呼喚句型「蜜塔這個功能…」「我覺得蜜塔…」 | 送語意裁決 | 一次便宜的 LLM 呼叫 |

關鍵分界是**喚醒詞後面有沒有停頓標點**：呼喚語必然有（STT 也確實會插逗號——
回報裡那個「,可以告訴我」就是證據），談論則直接黏名詞（「蜜塔這個功能」）。
單看位置不夠：「蜜塔剛才說截止日是六月三十號對吧」也在句首，但那是在向他人求證。

語意裁決在 `backend/src/sessions/response-policy.ts`（`ADDRESS_ARBITER_SYSTEM`）。
效果：回報 A.1 的四個誤觸發案例全部改為正確沉默。

**失敗退回策略很重要**：裁決呼叫失敗（Gemini 429）一律**退回舊行為照常回答**，
不可當成「沒在叫我」——否則額度一枯竭蜜塔就對所有非逗號句型全聾。

### 未完成：連續追問與多人對象追蹤

**A.3（沒喊名字的追問）** 目前仍只能靠 8 秒待命窗，接不上「那名額有限制嗎」這種
第二、三輪追問。正解是把定址併進插話決策層——那一層本來就在每輪話結束時看同一份
rolling window，問的是高度重疊的問題。這是下一步。

**已拍板的三點設計（2026-07-29 補記；先前只有第 1 點進了文件）：**

1. **每輪一次 LLM 呼叫同時產出 {定址, 意圖, 插話決策}**，取代目前 `classifyIntent`
   與 `INTERJECTION_DECISION_SYSTEM` 兩次高度重疊的呼叫。額度不增反減。
2. **保留正則快速路徑。** 句首呼喚仍立即 ack，維持 agent 模式的秒級回應；
   但「要不要答、答什麼」的裁決權交給決策層。（叫停指令同理，已於 07-29 落地。）
3. **`WAKE_PENDING_MS` 待命窗可退役。** rolling window 本來就有前幾輪，
   「那名額有限制嗎」「你可以再確認一次嗎」不需要這種用時間近似語意的 hack。

驗收：`meeting-scenarios.json` 中 A.3／A.3b 的 3 個 `knownFail` 轉為通過，回歸失敗維持 0。

⚠️ 動手前必須先取得可信基準（`--address` 跑出來沒有裁決失敗警告），
且 `eval-interjection.ts --variant live` 前後比對不可降——但注意該基準本身
有一個長期不穩定案例（見下）。

**A.4（多人會議不知道在回應誰）** 是**上游能力被換掉**，不是語意層問題：

- 舊的 Recall webhook 路徑有 `participant.name`，逐字稿知道誰在講話。
- 2026-07-28 啟用的 AGENT_MODE 走單軌混音轉錄，`agent-relay.ts` 一律送 `speaker: null`。

所以「👂 收到**的**問題」少了人名不是 bug，是這條路徑拿不到人名。調查結果：

- **OpenAI 這條走不通**：`gpt-4o-transcribe-diarize` 官方明載 Realtime API 不支援，
  只在批次的 `v1/audio/transcriptions` 可用（而且不支援 `prompt`，換過去會連
  「蜜塔」的詞彙偏置一起丟掉）。
- **Recall 這條走得通**：即時 webhook 支援 `participant_events.speech_on`/`speech_off`，
  payload 帶 `participant.name` 與 `timestamp.relative`（會議相對秒），
  而 agent relay 的 `elapsedSec()` 正好是同一個座標系。
  `recall-adapter.ts` 已經在訂閱 realtime 事件，只要多訂這兩個，在 session 維護
  「某時刻誰在講話」的時間軸，用 segment 的 `startTime` 反查名字即可。

**2026-07-29 已實作**（`backend/src/agent/speaker-timeline.ts`）。實作時改了兩處原始構想：

1. **不用 `timestamp.relative`，改用 epoch ms。** relative 的原點是 Recall 錄製起點，
   `elapsedSec()` 的原點是 `anchorMs`（admitted 時刻），兩者不保證同刻——原構想說的
   「同一個座標系」並不成立。寫入端改用 `timestamp.absolute`（沒有才退回收到當下），
   讀取端用 `Date.now()`，對齊問題整個消失。
2. **不是點查詢，是回看窗查詢。** agent-relay 的 segment `startTime` 是**轉錄完成**時
   才取的 `elapsedSec()`，不是開口時刻；等定稿事件到達時講者早已 speech_off，
   點查詢必然落空。改成查 [at-15s, at] 窗內誰講最久。

同時發言時回 `null` 不硬猜（標錯人比不標更傷）。順手修掉表面症狀：講者未知時
ack 文案原本無條件插「的」，印出破碎的「👂 收到的問題」，已改成分支文案。

**未驗證的部分（必須一場真會議才測得到）**：
- Recall 的 `participant_events.speech_on/off` payload 是否真的帶 `timestamp.absolute`
  （沒有的話走「收到當下」的退路，會多一段 webhook 送達延遲）
- webhook 送達延遲 ＋ 混音轉錄完成延遲的總和是否落在 15 秒回看窗內
- 多人交錯發言時的實際歸屬品質

單元測試（12 項 timeline ＋ 4 項 webhook 分派）只證明查表邏輯本身正確。

## 順帶修掉的潛伏 bug：Gemini 3.x 拒收 thinkingBudget

`lib/llm.ts` 原本**無條件**送 `thinkingConfig: { thinkingBudget: 0 }`。
這在 Gemini 2.5 系列是必要的（不關掉，思考 token 會吃光 maxOutputTokens 導致空回覆），
但 **Gemini 3.x 直接以 HTTP 400 "Request contains an invalid argument" 拒收**，
而且 3.x 預設就不思考（實測 `thoughtsTokenCount=0`），根本不需要關。

觸發條件：`GEMINI_INTERJECTION_MODEL` 的預設值正是 3.x 的 `gemini-flash-lite-latest`，
而 llm.ts 是「用 interjection key 就同時換 interjection model」。所以**只要一設定
`GEMINI_INTERJECTION_API_KEY`**（`.env.example` 與文件都建議設，用來隔離額度），
插話決策／沉默破冰／定址裁決會同時全部 400 陣亡，症狀只是「蜜塔忽然安靜了」，
錯誤只寫在 warn log 裡。

目前 `.env` 的 `GEMINI_INTERJECTION_API_KEY` 是**設了但留空**，所以走的是
`GEMINI_API_KEY` + 預設 `gemini-2.5-flash`，功能正常——這個 bug 一直沒被引爆。

已修：`buildGeminiGenerationConfig()` 依模型世代分流，並加上單元測試鎖住。

### 取得基準時踩到的兩個陷阱（寫下來避免重踩）

1. **429 會被吞成「裁決失敗」**，讓評測看起來像 prompt 改壞了。eval 現在會在總結
   明確印出失敗次數並警告該次數字不可信，且 LLM 呼叫預設間隔 5 秒。
2. **`docs/env_API-key` 裡的第 4 把（`test`）就是 `.env` 正在用的那把**（末四碼 `ao0w`）
   ——換 key 重跑前請先確認末四碼與 `.env` 不同，否則等於在同一個額度池裡重試。
   本次正式基準用的是第 1 把（`Gemeni API`）。
3. **換 key 不必改 `.env`**（2026-07-29 補）：shell 環境變數優先於 `--env-file`，
   直接前綴即可，跑完不留痕跡、也不必重啟後端：
   ```bash
   GEMINI_API_KEY=<另一把> npx tsx --env-file .env scripts/eval-meeting.ts --address
   ```
4. **`eval-interjection.ts` 預設會跑「全部變體」**（live ＋ v2 候選），額度吃兩倍。
   只要比對紅線基準時加 `--variant live`。
5. **eval-meeting 的裁決失敗警告原本沒接上**（2026-07-29 修）：`unknownCount` 只累加、
   從未印出，等於文件宣稱的守門根本不存在，429 照樣被讀成「prompt 改壞了」。
   現已在總結**數字之前**印出警告，並讓裁決失敗也回非零退出碼。
6. **「每次跑都剛好 1 次 429」是每分鐘速率上限，不是每日額度用完**（2026-07-29）。
   換三把不同 key（含全新未用的第 3 把）都一樣，5 秒間隔一律 1 次失敗；
   拉到 12 秒即零失敗。`--delay-ms` 預設已改為 12 秒。
   判讀原則：**失敗次數多（5 次以上）＝每日額度用完，要換 key 或等重置；
   固定 1–2 次＝間隔太密，放慢即可。**
